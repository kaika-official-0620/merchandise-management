# 検証サイトのログインエラーからの復帰

2026-09-15

## 原因

`staging_test_account_required` は、指定された検証用アカウント以外のユーザー名を `/login` または `/api/mobile/v1/session` に送ったときの拒否応答です。通常サイトのユーザー名は検証サイトでは使用できません。従来のブラウザ用ログインも JSON の 403 を返していたため、画面上でログインをやり直せませんでした。

今回、公開中の検証サイトへ架空の非検証ユーザー名を送信し、同じ 403 とエラーコードを再現しました。通常の GET、検証ユーザーの商品一覧・プラン画面、PostgreSQL のヘルスチェックは応答していました。

## 変更

- ブラウザで許可されないユーザー名を送った場合は、303 で固定の `/login` に戻し、日本語で検証用アカウントが必要と案内します。送られたパスワードやユーザー名を URL・セッションに保存しません。
- 検証サイトのログイン画面は、自己保管ユーザー・開花依頼ユーザー・開花担当者から選ぶ形式です。選択したアカウントの専用パスワードが必要です。
- 許可されない古いログイン状態も解除し、Web 画面ではログインに戻します。自動ログイン用 Cookie も解除します。
- アプリ API には引き続き JSON の 403 を返します。検証用アカウントの制限、パスワード認証、公開ファイルとヘルスチェックの例外を維持します。

## 開き直す URL

[開花の検証用ログイン](https://kaika-platform-staging.onrender.com/login)

上位機能まで確認する立場は「【検証用】開花依頼ユーザー」（`staging_business`）です。初期パスワードの確認場所は [検証環境の手順](staging-environment.md#初期アカウントと再実行)を参照してください。パスワードをチャットや URL に記載しないでください。

この修正は検証用の公開ブランチを対象とし、本番サービスや本番データへの反映は行いません。

## 反映前の確認

- `tests/test_staging_environment.py`：30 テスト成功。セッションと自動ログイン Cookie の解除、拒否後の未認証状態、API の JSON 応答、入力サイズ制限を含みます。
- `scripts/verify_staging_runtime.py`：実際のアプリを一時 SQLite に複製した 25 チェック成功。選択欄、ログインやり直し、3 役割のログイン、在庫、プラン、アプリ API を確認しました。
- このローカル検証は iPhone 実機や公開 PostgreSQL の試験ではありません。公開後の応答と画面を別途確認します。
